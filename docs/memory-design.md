## 记忆模块设计

### 当前设计

对话历史异步落库，达到一定长度后调一个轻量模型对历史对话进行压缩得到一个摘要。

### 优化方案

一句话总结：摘要设计从“一次LLM调用”升级为**按信息类型分层、以Turn为原子、支持增量更新的压缩管道**

#### 第一层：零压缩的结构化提取（优先做）

在调摘要模型前，先用一次结构化抽取，把 **事实、决策、目标、约束、未完成项** 从待压缩的 Turn 中抽出来，原样保留。这些信息不需要“总结”，需要的是**精确持久化**，如下所示：

```json
{
  "facts": ["预算 $50,000", "使用 PostgreSQL 15", "部署区域 us-east-1"],
  "decisions": [{"what": "选 serverless", "why": "避免运维负担"}],
  "constraints": ["用户要求所有输出用中文", "不能引入新的付费依赖"],
  "goals": ["完成用户认证模块"],
  "unresolved": ["错误处理还没写"]
}
```

#### 第二层：选择性摘要

+ 锚点Turn强制入选：包含用户首次陈述目标、包含 Decision、包含前一部抽出 facts 的Turn
+ 剩余 Turn 打分：初期可用启发式（关键词/是否含tool结果/时间衰减），不引入额外模型
+ 取top-K，但保留一个最低保护窗口（最近N个Turn）强制入选

#### 第三层：增量RollUp，而不是每次从零开始摘要

后续压缩把上一次的摘要作为输入，让模型“更新”它。每次压缩时连同“新增待压缩Turn + 结构化提取结果”一起交给轻量模型，prompt明确要求“在已有摘要基础上更新，保留仍然有效的事实和约束，修正已变化的进度”。

#### 第四层：摘要输出必须结构化

参考 Hermes 模板，推荐至少包含以下段落：

+ Goal：用户核心目标的当前表述（可能随对话演变更新）
+ Constraints & Preferences：硬性约束、用户偏好、系统设定
+ Progress - Done/In Progress/Blocked：已完成、进行中、阻塞项
+ Key Decisions：重大决策及理由
+ Facts：精确事实
+ Open Questions / Next Steps：待处理项
+ Provenance：本次摘要覆盖范围，用于回退

#### 注意事项

必须处理以下场景以及可能存在的其他异常场景：摘要模型上下文不足、摘要模型返回超时、输出的JSON不合法等。

需要有明确的降级方案：要么拆分成多次摘要再合并，要么保留原始Turn并标记“未压缩”，绝不能静默丢弃
